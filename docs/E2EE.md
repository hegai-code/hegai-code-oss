# Private machine — end-to-end encrypted sessions

Status: phase 1 (agent, hub, web) built 31.10.2026; smoke `private-machine-smoke`
passes. Phase 2: iOS built 12.11.2026 (see «As built, iOS» below); Android pairing and decryption: code and unit tests 12.11.2026 (see below; not yet run on a device against a live private machine).

## What it is

A machine owner can mark a machine **private**. From then on the content of its
sessions crosses the hub only as ciphertext: the hub routes it, stores it in the
replica, replays it — and cannot read it. Only devices the owner paired with the
machine hold the key.

Why: when a customer's sessions go through **our** hub (code.example.com) or when a
customer's security team requires that even their own hub not see transcripts.
A self-hosted hub (external edition) already keeps data in the customer's
perimeter; this is the stronger guarantee on top.

## Decisions (Owner, 31.10.2026)

- Option A: per machine, owner only. No team sharing of private machines in this
  version (members and managers see that sessions exist, not their content).
- Turning it on is the **machine owner's** act on the machine (`policy.json`),
  never a hub setting: a compromised hub must not be able to turn it off.

## Key

- One 256-bit content key `K` per private machine, generated by the agent on
  first enable, stored in the agent state dir (`<state>/e2ee.key`, 0600). Never
  sent to the hub in any form.
- Key id `kid` = first 8 bytes of SHA-256(K), hex. Sent in clear so clients know
  which key a ciphertext needs.
- Pairing: the owner runs `cc-remote-agent pair` (or `node agent.mjs --pair`) on
  the machine; it prints a pairing code `hcp1.<machineId>.<base64url(K)>` and,
  if `qrencode` exists, a QR of it. The web «Пары ключей» dialog accepts the code
  (paste); iOS/Android scan it (phase 2). Clients keep `K` locally (web:
  IndexedDB, a non-extractable WebCrypto `CryptoKey` imported once; iOS
  Keychain; Android Keystore-wrapped).
- Rotation: `--pair --rotate` makes a new `K`; old ciphertexts stay readable to
  clients that still hold the old key (clients keep a small key ring by `kid`).

## Envelope

AES-256-GCM, 96-bit random nonce. The AAD is `kid|machineId|dir|kind|id`
(UTF-8; the machine id is the machine's own, so ciphertext of one machine never
opens as another's), where `dir` is `a2c` (agent to client) or `c2a` (client to agent) and
`kind|id` says what the envelope is for, so a hub cannot lift an envelope onto
another frame or turn it around:

| Frame | `kind` | `id` |
|---|---|---|
| `stream`, `run_status` | the frame type | `runId` |
| `tool_request`, `tool_decision` | the frame type | `requestId` |
| `term_data`, `term_input` | the frame type | `termId` |
| `input`, `open`, `new_session`, `takeover`, `resume` | `turn` | empty (see below) |
| `set_permission_mode` | the frame type | `runId` |
| `rpc_request`, `rpc_response` | `rpc` | `requestId` |
| history message (any carrier) | `msg` | message `uuid` (always `a2c`) |
| summary title / place | `title` / `cwd` | `sessionId` (`a2c`) |
| `turnE2e` and the hub's `user_turn` | `turnecho` | empty (`c2a`, no epoch) |

```json
{ "e2e": 1, "kid": "a1b2c3d4e5f60718", "n": "<base64 nonce>", "c": "<base64 ciphertext+tag>" }
```

**Epoch.** Every client-to-agent envelope's `dir` is `c2a:<epoch>`, where the epoch
is a random id the agent makes per process and announces in its register
(`MachineInfo.e2eEpoch`, sent whenever the machine holds a key). A recording of
commands is therefore dead after the agent restarts. A hub that lies about the
epoch only makes commands fail.

**Turn frames share one binding.** The hub turns a browser's `open` into an
`input` (a run exists), a `resume` or a `takeover`, and `new_session` has no id
yet, so all of them bind to `c2a:<epoch>|turn|`. What each envelope is FOR is
inside it: `_k` (the frame kind the client made), `_r` (run), `_s` (session). The
agent compares them with the frame it received (`checkOpened`): an `input`
envelope is not a `new_session`, an `open` for session A is not accepted into a
run of session B.

**The person's choices are sealed.** `new_session` seals `cwd`, `model`,
`effort`, `permissionMode` with the message (the clear copies stay as routing
hints for the hub; on opening the sealed ones replace them). A `tool_decision`
seals `allow`, `permissionMode`, `updatedInput`, `message`, and
`set_permission_mode` seals `mode`; on a private machine the agent refuses all
three unless they arrive sealed.

Nothing is deployed yet, so the format stays `e2e:1`. The agent also remembers
every inbound nonce for the life of the process and refuses a repeat (up to 200k;
past that it refuses sealed commands until restart), so a replayed command does
not run twice. On opening, every content field of a frame is replaced by the
envelope's (a clear field left next to an envelope never survives), and the agent
refuses a command that carries content in the clear whether or not it also has an
envelope.

The plaintext is the UTF-8 JSON of the field(s) being replaced. Available in
Node `crypto`, WebCrypto (`AES-GCM`), CryptoKit (`AES.GCM`), Android
`Cipher("AES/GCM/NoPadding")`.

## What is encrypted (private machine only)

| Frame / store | Encrypted | Clear (routing metadata) |
|---|---|---|
| `stream` events | `event.text`, `event.raw`, `event.data` → one envelope in `event.e2e` | `kind`, `code`, ids, state |
| user input (client → agent) | `text`, `images`, `files` → `e2e` | runId, sessionId, sizes |
| `user_turn` (hub → other screens) | forwarded envelope as is | ids |
| `tool_request` | `input`, `title` → `e2e` | tool name |
| `session_sync_chunk` (replica) | each message → `{uuid, type, e2e}` | uuid, type |
| `session.messages` / history pages | messages as stored (ciphertext) | paging |
| `rpc_response`, every method except `models.list` and a plain `{ok:true}` (`runtime.job.status` is sealed) | whole `result` → `{e2e}`; an `ok:false` `error` text → `e2e` (placeholder in `error`) | ok |
| `run_status` | `error` → `e2e` | state, code |
| `term_data`, `mirror_data` | data → envelope | termId |
| session summary `title` | → `titleE2e` envelope, `title` = «Зашифровано» | cwd basename? **no** — `project` and `cwd` are encrypted too (`cwdE2e`); the hub keys sessions by id |

## What the hub does differently for a private machine

The agent reports `private: true` in `register`. The hub then:
- never builds text from content: no `provisional_title`, no `preview`, no
  `lastText`, no enrich, no push body beyond «сессия N: ожидает ответа» — the push
  title is the generic machine name;
- skips `trim_tool_payloads` on these messages (cannot read them) — clients trim;
- excludes the machine from the conversation archive, the task board, the
  Telegram bot's history document and `fleet` send/status with text (403
  `private_machine`);
- refuses sharing this machine's projects (`project_shares` for a private
  machine → 409) and support access sees nothing either;
- `user_turn` is built from the envelope, not from text.

## Clients

- A client without the key shows «Зашифровано на машине — нужен ключ» with a
  «Ввести код пары» button; session list shows «Зашифрованная сессия».
- With the key: decrypt envelopes on receipt (stream, history, rpc results,
  terminal) and encrypt outgoing input/rpc params that carry content (`fs.write`
  body, terminal input, `input.text`).
- Dictation `/polish` and suggestions are off for private sessions (they would
  send plaintext to the hub).

## Threat model, honest

Protects transcript content and file contents from the hub operator, the hub's
database and backups. Does **not** hide metadata (which machine, when, how much,
tool names), does not protect against a malicious **web bundle** served by the
same hub (web clients run code the hub serves — a hub that is compromised can
serve JS that exfiltrates the key; native apps from the stores are not served by
the hub). For the web this is defence against a passive or honest-but-curious
hub, not against an active one. The pairing code is the key: whoever sees it can
read the sessions.

## As built, phase 1 (31.10.2026) - where it differs from the sketch above

- **Switch**: `"private": true` in `policy.json` (or `node agent.mjs policy
  private on`; `CC_REMOTE_PRIVATE=1` can only switch it ON). Only a literal
  `true` counts; any other value is logged as an error and ignored (not
  private, no crash). An unreadable (malformed) policy file keeps the LAST
  VALID reading of the switch, remembered in `<state>/private.last` each time a
  valid policy loads; with none it is not private. A key file left over from
  `private off` therefore does not make a typo private.
  `acceptPlaintextInput: true` (owner only) lets an old client without the key
  type in; default false: the hub AND the agent refuse content in the clear, and
  the agent also refuses an unsealed `new_session`, `tool_decision` and
  `set_permission_mode`. With the flag on, the agent takes all of those unsealed
  (an old client has no way to seal them); a sealed one is still opened and its
  sealed values still win over the clear ones.
- **Pairing**: `node agent.mjs --pair [--rotate]` (also `pair`). Keys: current in
  `<state>/e2ee.key`, retired ones in `<state>/e2ee.retired` (still opened by
  the agent, never used to seal). `kid` is 16 hex chars.
- **AAD** is `kid|machineId|dir|kind|id` (see Envelope); the envelope is `{e2e:1, kid, n, c}`. A sealed rpc request also repeats its method and its clear path-like params (`cwd`, `path`, `dir`, `name`, `uploadId`, `from`, `to`, `sessionId`) inside the secret, and the agent compares them with what it received. Vectors
  every side is held to: `shared/test/e2e-vectors.json`.
- **Traversal** (which fields are content) is `shared/src/e2e.ts`, one table
  for every frame; the agent seals at its one send door (`sendRaw`) and opens
  at its one receive door (`onMessage`); the web seals in `useCentral.send` and
  opens in `ws.onmessage`, so nothing downstream changed.
- **Summaries**: `title` is the placeholder, the real one is `titleE2e`;
  `cwd`/`project`/`gitBranch` are absent and sealed together as `cwdE2e`.
  The hub therefore has no cwd for a private session: a resume carries none and
  the agent reads the folder of a session id from its own inventory.
- **Input**: one envelope for the agent (`e2e`), and a second, light one
  (`turnE2e`: text, image count, file names) that the hub forwards as the
  `user_turn` for the other screens - so they need not carry attachment bytes.
- **Never sent** by a private agent: `memory_push`, `builder_profile`,
  `project_pushed`, `session_committed.cwd`, the process list in
  `machine_stats.top`.
- **Becoming private** (a real false -> true change of the stored row, at most
  once per 6 h per machine) purges the plaintext the hub holds for the machine:
  replica, speech archive, this machine's board links (a card that also covers
  other machines stays; the global watermark is untouched), the live runs'
  title/preview/text/replay, the stored builder profile and process list, and the
  machine's project shares. It is fail-closed: if the purge fails the register is
  refused and the agent retries. Going private -> off purges the replica the
  same way, so the agent (whose catalog then comes back empty) re-uploads the
  transcripts in the clear. A private agent declares its live runs without a
  folder. A rotated key (`--pair --rotate` in another process) is picked up by
  the running daemon (checked on outgoing frames and on an unknown `kid`).
- **Hub**: `machine_private()` is read from the live registration, else from
  the stored machine row. No title/preview/lastText/push body/enrich for such a
  run; `fleet` send/status/spawn -> 403 `private_machine`; a project share ->
  409; `archive-conversations.py` and `board-assemble.py` (and so
  `release-sessions.py`) skip the machine; the Telegram bot does not list it.
- **Web**: keys in IndexedDB (`cc-e2ee`) as non-extractable `CryptoKey`s; the
  dialog is opened from the machine's card on «Железо» and from the banner a
  session shows while this browser holds no key. Pairing reloads the page. The
  decrypted transcript is not written to the local cache; the microphone
  (hub-side speech recognition) and suggestions are off for private machines.

### Self-update and the threat model

A private machine keeps the content key on its disk. The **internal** edition's
self-updater installs whatever `agent.mjs` the hub serves, and a bundle can read
`e2ee.key`, so on a private machine the internal edition **does not self-update**
(logged at start; the owner re-runs the installer). The **external** edition,
whose updater accepts only a bundle with a release signature the hub cannot
forge (`verifyRelease`), still updates itself.

The browser decides to seal by its own key ring and by the machine IT named in
its open / new_session (answered by `opened` for the same machine); the hub's
active-run list never moves a run to another machine. For a machine whose key a
browser holds, clear assistant text, tool prompts and user turns are dropped, not
shown, and no enrichment request is made for it. When a machine stops being
private the browser must forget the key («Ключ остался · забыть» on the machine's
card) to read its now-clear output; an agent that is no longer private but still
has `e2ee.key` still opens a paired browser's sealed commands.

### Known limits of phase 1

- Clear on the wire for a private machine, by design of the routing: machine
  and session ids, tool names, event kinds/codes, timestamps and sizes, file
  and folder PATHS in `fs.*`/`git.*` params, `new_session.cwd` (the project
  picker's choice), the project list's names unless sealed (`projects.list` is
  sealed on the way back, not on the way in).
- Session categories do not apply to a sealed first turn (the hub cannot
  prefix a skill to text it cannot read).
- `session.image` results are sealed, so the hub cannot shrink them.
- The hub's «background tasks» / sub-agent replay and `turn_usage` read
  `event.data`, which is sealed: late subscribers do not get them replayed.
- iOS (1.0.64) and Android pair by QR or pasted code and work with a private
  machine like the web: see «As built» for each below. A client older than that
  shows the placeholder title and empty messages and cannot type into a private
  machine (the hub refuses plaintext).

## As built, phase 2: Android (12.11.2026)

The traversal and cipher are a line-for-line Kotlin port of `shared/src/e2e.ts` and
`web/src/e2ee/crypto.ts` (`android/core/.../E2ee.kt`, javax.crypto `AES/GCM/NoPadding`,
pure JVM). `E2eeTest` passes `shared/test/e2e-vectors.json` and opens frames sealed by
the real agent-side traversal with Node crypto (`core/src/test/resources/e2e-agent-frames.json`);
frames Kotlin seals were opened by the agent's `collectOpen` + `checkOpened` in a one-off
cross check.

- **Keys**: `E2eeStore` keeps one key per pairing code, encrypted by an AES key that lives
  in the Android Keystore (alias `hegai-e2ee-ring`, AAD = key id + machine), as ciphertext in
  `noBackupFilesDir/e2ee-ring.json`; the app has `allowBackup=false`. Unwrapped keys are held
  in memory. Sign-out of the hub account keeps them (they belong to device and machine);
  «Забыть ключ» (pairing dialog, reached from the session menu, the locked banner and
  Settings → the machine's card) removes them.
- **Pairing**: «Ввести код пары» = Google code scanner (`play-services-code-scanner`, a
  system dialog: no CAMERA permission, the app never sees a frame) or paste. The code is
  parsed by `parsePairingCode`; a code for another machine than the one on screen is refused.
  After a pairing or a forget the socket reconnects (what had arrived was placeholders).
- **Receive** (`HubEngine.openIncoming`, one door): envelopes open only under the machine
  the client itself attributes the frame to (its own rpc / mirror / run bookkeeping, as
  `machineOfFrame` on the web); clear assistant text, tool prompts and user turns for a keyed run are
  dropped; an `opened` that names another machine than the open asked for is dropped.
- **Send** (`HubEngine.send`, one door): sealed when the ring holds the machine's key (the ring
  decides, not the hub's flag), or when the hub says private (then: no key = refused with the
  pairing hint, nothing sent; no epoch yet = refused). A content frame that cannot be placed on
  a machine while any key is held or any machine is private is refused. Bare `open`,
  `subscribe`, `projects.list` carry nothing and go as is.
- **Off for private machines**: hub-side suggestions/titles (`enrich_request`), server
  dictation and polish (the phone's own recogniser is used), the notification «Разрешить/Запретить»
  action (decide in the app, sealed), prefetch of history.
- **At rest**: the decrypted transcript, titles and folders of a private machine are not written to
  the phone's cache (the account cache keeps the machine's sessions as «Зашифровано»). Drafts and an
  unconfirmed outgoing message are kept as for any machine (device-local, Keystore-encrypted).
- **UI**: a private machine without a key shows «Зашифровано на машине — нужен ключ» with the
  pair button above a disabled composer; session lists read «Зашифрованная сессия».

## As built, iOS (phase 2, 12.11.2026)

Code: `ios/CCRemoteKit/Sources/CCRemoteKit/` - `Protocol/E2eeTraversal.swift` (the
table, bindings, seal/open traversal: a port of `shared/src/e2e.ts`, Foundation
only, runs under `check-protocol-linux.sh`), `E2EE/` (CryptoKit cipher, Keychain
key ring, inbound opener, outbound decision), `Net/CentralClient+E2ee.swift`;
UI in `ios/CCRemote/Features/Privacy/`. Tests: `E2eeTests` (the vectors of
`shared/test/e2e-vectors.json`, ring, inbound, outbound, client end to end),
`E2eeTraversalTests`.

- **Pairing**: «Ввести код пары» - scan the QR the agent prints (AVFoundation,
  `NSCameraUsageDescription`) or paste `hcp1.<machineId>.<key>`. From the machine's
  card on «Железо» and from the locked session. A code for another machine than the
  one in front of the person is refused. The code is cleared from the clipboard
  after a successful paste.
- **Key storage**: one Keychain item `e2ee-keyring` (JSON of `{kid, machineId, key,
  addedAt}`), `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not synchronised.
  «Забыть ключ» per machine; deleting the account's local data deletes all keys.
- **Receive**: `CentralClient.onText` runs `E2eeInbound` before the typed decoder,
  off the main actor: envelopes open under the machine THIS phone attributes the
  frame to (its own record of run / rpc / terminal / mirror, the same bookkeeping
  as the web); clear assistant text, tool prompts or user turns for a run of a
  keyed machine are dropped; summaries (`titleE2e`/`cwdE2e`) open in the lists.
- **Send**: `CentralClient.send` -> `e2eeWire`: a frame that carries content for a
  machine whose key is held is sealed (AAD `kid|machineId|c2a:<epoch>|...`, the
  `turnE2e` echo, sealed rpc params with `_m`/`_p`); for a private machine without
  a key, or a frame that cannot be placed on one machine, nothing is sent
  (fail closed) and the pairing sheet opens. A missing epoch fails the send.
- **Never on this phone's disk or at hub services for a private machine**: the
  decrypted transcript is not written to the transcript cache, the fleet snapshot
  leaves private machines out, no offline outbox, no navigation-title generation,
  no enrichment, dictation (hub recognition and polish) is off, the start screen
  sends no category.
- **Locked state**: a private machine without a key shows «Зашифровано на машине -
  нужен ключ» with the pair button instead of a transcript and composer.
- **Not done**: the Watch/Live Activity/widget surfaces and drafts typed in the
  composer are not special-cased; the push-notification approve/deny action for a
  private machine goes to the hub in the clear and the agent refuses it (a tool
  decision must arrive sealed).
