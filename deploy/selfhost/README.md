# Hegai Code на своём сервере

Hub (центральный сервер Hegai Code) в Docker: сам hub и Caddy с автоматическим
HTTPS. Агенты работают на ваших машинах и сами звонят на hub — входящих портов
на машинах не нужно. Описание редакции — [docs/EXTERNAL-EDITION.md](../../docs/EXTERNAL-EDITION.md).

## Что нужно

- Сервер с Ubuntu 24.04 (другой Linux с Docker подойдёт). Для команды из
  10–20 человек 8 vCPU / 32 ГБ / 200 ГБ более чем достаточно: сам hub съедает 1–2 ГБ
  и несколько ГБ диска (SQLite с историей сессий); остальное — под агентов
  и проекты, если они живут на этом же сервере.
- Docker Engine с плагином Compose v2 (`docker compose version`).
- Доменное имя, A/AAAA-запись которого указывает на этот сервер, и открытые
  порты 80 и 443 (Let's Encrypt проверяет домен по 80-му).
- С любого устройства людей — исходящий доступ к этому домену по 443.

## Установка

```bash
git clone <репозиторий> hegai-code && cd hegai-code/deploy/selfhost

sudo ./install.sh code.example.com owner@example.com
```

Название в интерфейсе (лого в боковой панели, вкладка, экран входа) установщик
берёт из домена: `code.anomaly.ru` → «Anomaly Code», лого «anomaly.code» — и в
терминале спрашивает, оставить ли (Enter — да). Своё — третьим аргументом:
`sudo ./install.sh code.example.com owner@example.com "Example Code"`. Поменять
потом — `CC_REMOTE_BRAND_NAME` в `.env` и `docker compose up -d`.

`install.sh` делает всё по порядку и безопасно перезапускается: `init.sh`
(`.env` с секретами), `docker compose up -d --build` (первая сборка — 10–20
минут), `connect-host.sh` (этот сервер подключается сам, без кодов) и в конце
печатает одноразовую ссылку настройки владельца. По шагам руками — те же
четыре команды.

1. Откройте ссылку, которую напечатал `install.sh` (владелец = e-mail из
   `CC_REMOTE_BOOTSTRAP_EMAIL`): задайте пароль и подключите приложение-
   аутентификатор (Google Authenticator и подобные). Код из аутентификатора
   понадобится для одобрения обновлений агента.
2. Этот сервер уже подключён: `connect-host.sh` создаёт пользователя `hegai`
   (с linger), ставит под ним агента (systemd --user) и входит одноразовым
   секретом `CC_REMOTE_HOST_ENROLLMENT_SECRET` из `.env`. Если npm не собрал
   `node-pty`: `apt-get install -y build-essential python3` и повторить скрипт.
   Другие машины (Linux, macOS), на каждой:

   ```bash
   curl -fsSL https://code.example.com/go | bash
   ```

   Windows (PowerShell): `irm https://code.example.com/go.ps1 | iex`.
   Агент покажет короткий код — подтвердите его на `https://code.example.com/link`
   с любого устройства, где вы вошли. Агент ставится в профиль пользователя,
   без прав администратора, и сам поднимается после перезагрузки.
3. Войдите в Claude Code и Codex **своими корпоративными аккаунтами** — второй
   экран после первого входа или «Настройки → Машины»: «Установить», если на
   машине ещё нет `claude` / `codex`, затем «Войти» (или `claude` /
   `codex login` в терминале машины). Общего ключа и чужой подписки в этой
   редакции нет.
4. Остальные сотрудники: через OIDC (если заданы `OIDC_*`) или по приглашению.
   Владелец сервера создаёт команду («Команда → Люди → Создать команду»; та же
   карточка есть в «Настройки → Аккаунт»), жмёт «Пригласить» и отправляет
   человеку ссылку любым способом (письма hub не шлёт). Для нового
   адреса ссылка ведёт на настройку пароля и кода аутентификатора и сразу
   добавляет в команду; действует 7 дней, одноразовая, отзыв приглашения её
   гасит. Учётки по приглашению заводит только администратор сервера (владелец
   по умолчанию).
   Добавить человека **без команды** — «Команда → Доступ» (`/w/admin`, видна
   администратору): карточка «Добавить человека» выдаёт одноразовую ссылку на
   24 часа. Там же у каждой активной локальной учётки есть «Сбросить вход» —
   если человек потерял телефон с аутентификатором: пароль и код сбрасываются,
   сессии завершаются, выдаётся новая ссылка.
5. Телефон. Приложение (App Store / Google Play) подключается к вашему серверу
   так: откройте `https://code.example.com/app` на компьютере и наведите камеру
   телефона на QR («Открыть в приложении»), либо на экране входа в приложении
   у строки «Сервер» нажмите «Свой сервер» (Android — «Другой сервер») и
   отсканируйте тот же QR или введите адрес сервера. После настройки входа по ссылке на телефоне
   страница сама предложит «Открыть в приложении».

Проверка: `curl -fsS https://code.example.com/health` отвечает `{"ok":true}`;
`docker compose ps` показывает `hub` в состоянии `healthy`.

## Настройка

Всё — переменные окружения в `.env`; полный список с пояснениями — в
[.env.example](.env.example). Обязательные три: `HEGAI_DOMAIN`, `CC_REMOTE_TOKEN`
(≥ 32 символов, hub с коротким не стартует), `CC_REMOTE_BOOTSTRAP_EMAIL`.
Остальное по желанию: вход через OIDC/Google/Telegram, название продукта
(`CC_REMOTE_BRAND_NAME`), собственные страницы политики/поддержки
(`CC_REMOTE_LEGAL_DIR`), LLM-шлюз (свой или из комплекта — `llm.sh`, см. ниже). Всё, что не задано, выключено; адресов
HegAI в настройках по умолчанию нет. После правки `.env`:
`docker compose up -d` (пересоздаст то, что изменилось).

Свои страницы политики конфиденциальности, поддержки и удаления аккаунта:
положите `privacy.html`, `support.html`, `delete-account.html` в
`deploy/selfhost/legal/`, раскомментируйте монтирование `./legal:/legal:ro`
в `compose.yml` и задайте `CC_REMOTE_LEGAL_DIR=/legal`. Без этого hub показывает
нейтральную страницу «за обработку данных отвечает оператор этого сервера,
обратитесь к администратору».

## Свой LLM-шлюз: подписки и другие модели (необязательно)

Без шлюза каждый подключает свои Claude и Codex на своей машине — это работает
всегда. Шлюз добавляет к hub один адрес `https://<домен>/llm/v1` для всех
моделей, отдельный ключ `sk-bf-…` каждому человеку, лимиты и вкладку «Расходы».
Внутри — [Bifrost](https://github.com/maximhq/bifrost) и
[CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI), устроенные так же,
как шлюз, которым пользуются сами разработчики Hegai Code: **одна учётка
подписки = один контейнер CLIProxyAPI = один пул `pool-<имя>` в Bifrost**.

```bash
cd deploy/selfhost
sudo ./llm.sh enable              # Bifrost, hub перезапускается со шлюзом
sudo ./llm.sh add-account main    # учётка подписки ChatGPT/Codex
sudo ./llm.sh login main          # ссылка + код: войти и подтвердить ОБА шага
sudo ./llm.sh status              # провайдеры, ключи людей, модели
```

Ещё учётки — `add-account <имя>` и `login <имя>` для каждой: ключи людей ходят во
все пулы, модель без префикса (`gpt-5.6-sol`) Bifrost раскладывает по пулам и при
отказе одного уходит в другой; `pool-<имя>/<модель>` — строго в одну учётку.
Закрепить человека за одной учёткой — оставить у его ключа один пул в админке.

Другие модели — любой OpenAI-совместимый API (ключ спросит скрыто, в истории
команд его не будет):

```bash
sudo ./llm.sh add-provider router https://openrouter.ai/api/v1
sudo ./llm.sh add-provider ds https://api.deepseek.com/v1
sudo ./llm.sh add-provider local http://172.17.0.1:11434/v1      # Ollama на этом сервере
sudo ./llm.sh add-provider oai https://api.openai.com/v1 --responses
```

Модель тогда называется `<имя>/<модель>` (`ds/deepseek-chat`). Имена встроенных
провайдеров Bifrost (`openai`, `openrouter`, `deepseek`, `ollama`, `groq`,
`mistral`, `gemini`, `anthropic`, `xai`, `vllm`…) заняты — `add-provider` под
ними откажет. `--responses` — для сервисов, которые понимают Responses API;
остальным Bifrost сам переводит запросы Codex (он ходит только Responses) в Chat
Completions. Встроенные провайдеры (Anthropic, Gemini, Bedrock, Azure…) и тонкая
настройка — в админке Bifrost: `sudo ./llm.sh ui` открывает её на
`127.0.0.1:8099`, пока команда работает (с другого компьютера —
`ssh -L 8099:127.0.0.1:8099 root@<сервер>`); логин `admin`, пароль —
`LLM_ADMIN_PASSWORD` в `.env`. После правок в админке — `sudo ./llm.sh sync`:
шаблон `hegai:template-community` и ключи людей получают маршруты ко всем
провайдерам с ключом (то, что вы настроили у ключа — лимиты, запрещённые
модели, — сохраняется).

**Ключи людей.** `sudo ./llm.sh seat anna@example.com bob@example.com` создаёт
ключ `hegai:<почта>` по шаблону `hegai:template-community` (маршруты и лимиты
копируются с него; лимиты шаблона и отдельных ключей — в админке). Человек видит
свой ключ, адрес и готовую команду настройки Codex на странице
`https://<домен>/access`, там же — лимиты; почта ключа должна совпадать с почтой
его учётки в hub.

**Машины.** Агент пускает Codex через шлюз (сессии «только через шлюз», журнал,
лимиты в приложении), только если владелец машины сам назвал этот шлюз:
`CC_REMOTE_GATEWAY_URL=https://<домен>/llm/v1` в окружении службы агента. Для
этого сервера `llm.sh` и `connect-host.sh` прописывают это сами
(`/etc/systemd/user/cc-remote-agent.service.d/hegai-gateway.conf`; это удобство,
а не граница — пользователь агента может перекрыть адрес своим
`~/.cc-remote/env`); на остальных машинах — вручную, hub этот адрес задать не
может.

**Безопасность и данные.**
- Наружу через Caddy открыты только эндпоинты инференса (`/llm/v1/models`,
  `/responses`, `/chat/completions`, `/completions`, `/embeddings`), каждый — по
  ключу человека. Админка Bifrost снаружи не открыта и закрыта паролем
  (`LLM_ADMIN_PASSWORD`); по сети её видно с самого сервера (адрес контейнера
  в мосте docker — в том числе из сессий агента, поэтому пароль обязателен),
  из сети compose (hub) и через `llm.sh ui`.
- Тексты запросов Bifrost не хранит (`disable_content_logging`), метрики — 7 дней.
- Всё состояние — в `deploy/selfhost/llm/` (root, 0700): база Bifrost (ключи
  людей и провайдеров) и **токены входа в учётки подписок**. Не коммитьте и не
  отдавайте эту папку; в резервную копию — вместе с `.env`.
- `sudo ./llm.sh disable` выключает шлюз, папка `llm/` остаётся.
- Сервер со своим nginx вместо Caddy: Caddy в `compose.override.yml` уведён в
  профиль, hub опубликован на `127.0.0.1:4319`, а `compose.llm.override.yml`
  публикует Bifrost на loopback (`bifrost: ports: ["127.0.0.1:8098:8080"]`).
  `llm.sh` сам добавляет оба файла в `COMPOSE_FILE`, если они есть. В nginx
  повторите маршруты из `Caddyfile`: наружу только `/llm/v1/{models,responses,
  chat/completions,completions,embeddings}` (без префикса `/llm`), остальное
  под `/llm/` — 404, `/hegai/limits` → hub `/api/gateway/key-limits`.

**Условия подписок — на вас.** Учётка подписки обычно рассчитана на одного
человека: несколько людей на одной учётке нарушают правила провайдера и ведут
к блокировке. CLIProxyAPI настроен без маскировки и с осторожными повторами
внутри учётки, но Bifrost при отказе пула может отправить запрос в другой пул, и
от правил провайдера это всё равно не освобождает. Если команде нужен общий доступ — подключайте API-ключи
(`add-provider`).

## Данные и резервные копии

Всё состояние — в одном томе `hub-data` (`/data` в контейнере): SQLite-база
(аккаунты, машины, реплики сессий) и каталог одобренных релизов агента.
Журналы — в stdout (`docker compose logs`), на диск hub ничего больше не пишет.
Со включённым LLM-шлюзом (`llm.sh`) к этому добавляются `deploy/selfhost/llm/`
(база Bifrost, ключи людей и провайдеров, токены входа в учётки подписок) и
`.env` (пароль админки шлюза): копируйте их вместе с томом, лучше при
остановленном шлюзе (`docker compose stop bifrost`), и храните как секрет.

Резервная копия без остановки (согласованный снимок SQLite):

```bash
mkdir -p backup
docker run --rm -v hegai-code_hub-data:/data -v "$PWD/backup":/backup debian:bookworm-slim sh -c \
  "apt-get update -qq && apt-get install -y -qq sqlite3 >/dev/null \
   && sqlite3 /data/cc-remote.sqlite3 \".backup '/backup/cc-remote-$(date +%F).sqlite3'\""
```

Либо остановить и скопировать том целиком (надёжнее всего):

```bash
docker compose stop hub
docker run --rm -v hegai-code_hub-data:/data -v "$PWD/backup":/backup debian:bookworm-slim \
  tar -C /data -czf /backup/hub-data-$(date +%F).tgz .
docker compose start hub
```

Восстановление: `docker compose down`; `docker volume rm hegai-code_hub-data`;
`docker volume create hegai-code_hub-data`; распаковать архив в том
(`tar -xzf … -C /data` в таком же временном контейнере); `docker compose up -d`.
Если имя проекта другое (`COMPOSE_PROJECT_NAME`), том называется
`<проект>_hub-data`. Храните копии вне этого сервера. Сертификаты (том
`caddy-data`) копировать не обязательно — Caddy выпустит их заново.

## Обновление

```bash
cd hegai-code && git pull
cd deploy/selfhost && docker compose up -d --build
```

Hub перезапустится за секунды; агенты переподключатся сами. Новая версия
агента, которая приехала вместе с hub, **не раздаётся сразу**: она ждёт, пока
владелец одобрит её в административном интерфейсе кодом из аутентификатора
(и должна нести подпись вендора — неподписанный пакет hub не отдаёт). Только
после одобрения агенты на машинах обновляются сами.

Откат: вернуть предыдущий коммит и снова `docker compose up -d --build`;
схема базы расширяется только вперёд, поэтому перед обновлением сделайте копию
тома (см. выше).

## Уведомления на телефон

Ключей Apple/Google для наших приложений у вашего hub нет, поэтому пуши
(«агент ждёт ответа», «ошибка», «есть ответ») он отправляет через релей вендора: нужны
`CC_REMOTE_PUBLIC_URL` и адрес релея `CC_REMOTE_PUSH_RELAY_URL` (выдаёт вендор). К нам уходят токен устройства,
id сессии/машины/пользователя, состояние и время — без текста сессий. Выключить:
`CC_REMOTE_PUSH_RELAY=off` (подробности в `.env`).

## Приложения на компьютер и телефон

Телефон: приложения Hegai Code из App Store и Google Play; на экране «Телефон»
и странице `https://<домен>/app` — QR и ссылки, в приложении «Другой хаб» →
ваш домен. Mac/Windows-приложение hub предлагает, только если задан
`CC_REMOTE_APP_DL` (адрес подписанных сборок, выдаёт вендор): своего `/dl` у
этого hub нет. Без него на всех ОС предлагается агент одной командой `/go`.

## Подписанный релиз агента

Образ при сборке кладёт в `/app/agent-release` подписанный релиз из
`deploy/selfhost/agent-release/`, если вендор положил туда файлы (`agent-external.mjs`
и подписи, `*.sig`). Если каталог пуст, собирается неподписанный пакет агента:
образ запускается, но hub не раздаёт его агентам — получите подписанный релиз у
вендора и пересоберите.

## Песочницы для сотрудников (необязательно)

Сотрудникам без своего компьютера можно выдавать изолированных Linux-
пользователей с агентом на этом же хосте. Это отдельный модуль уровня хоста,
не часть контейнеров: [deploy/sandbox/SANDBOX.md](../sandbox/SANDBOX.md)
(`install-host.sh`, демон `cc-remote-provisioner`). Что важно для этой
установки:

- Песочницы живут на хосте, а не в Docker; граница — unix-пользователь.
- Агенты в песочницах ходят на hub по его **публичному https-адресу**:
  в `/etc/cc-remote/provisioner.env` задайте `CC_REMOTE_HUB_URL=https://code.example.com`.
  Пакет агента они берут с `/install/agent.mjs` самого hub.
- Ключ провижинера: `CC_REMOTE_PROVISIONER_TOKEN` (≥ 32 символов, одинаковый в
  `.env` hub и в `provisioner.env`).
- Осторожно с `install-host.sh --egress`: фильтр пускает песочницы только на
  22/80/443 внешних адресов и закрывает loopback и порты вне `sandboxes.slice`.
  Обращение к hub по публичному адресу этого же сервера уходит через loopback и
  может быть отрезано — проверьте `curl https://<домен>/health` из-под
  песочницы после включения; если не проходит — держите песочницы на отдельном
  хосте или не включайте `--egress`.

## Twelve-factor

| Фактор | Как выполнен |
|---|---|
| I. Кодовая база | Один репозиторий, один образ; редакция выбирается переменной `CC_REMOTE_EDITION=external`, а не форком. |
| II. Зависимости | Явно: `Cargo.lock`, `package-lock.json`, базовые образы закреплены тегом и digest; в образе всё нужное (hub — один статический по зависимостям бинарник + собранный web). |
| III. Конфигурация | Только окружение: `.env` → `environment` контейнера. В образе нет ни доменов, ни секретов; не заданное выключено, адресов HegAI по умолчанию нет. |
| IV. Подключаемые сервисы | Внешние сервисы (OIDC, Google, Telegram, LLM-шлюз, распознавание речи) — URL и ключи в переменных; заменяются без пересборки. |
| V. Сборка, релиз, запуск | Сборка — `docker build` (Dockerfile), релиз — образ + `.env`, запуск — `docker compose up`. Версии агента проходят отдельное одобрение владельцем. |
| VI. Процессы | Hub не хранит состояние в памяти процесса сверх сокетов: всё в SQLite на томе; корневая ФС контейнера read-only, `/tmp` — tmpfs. |
| VII. Привязка портов | Hub сам слушает `0.0.0.0:4319` (`PORT`) и никуда не публикуется; наружу — только Caddy на 80/443. |
| VIII. Параллелизм | Масштаб — число агентов-машин, они сами звонят на hub; hub — один процесс на одну SQLite (по дизайну один писатель). Вертикально — `HEGAI_HUB_MEM`. |
| IX. Утилизируемость | Быстрый старт (секунды), корректный останов по SIGTERM, `restart: unless-stopped`, healthcheck `/health`; агенты и клиенты переподключаются сами. |
| X. Паритет окружений | Один и тот же образ на dev/stage/prod; разница только в `.env`. Локальный запуск — тот же compose с другим доменом. |
| XI. Журналы | Только stdout/stderr, без файлов; собирает `docker logs`/ваш драйвер журналов. Журнал аудита действий — в самом продукте. |
| XII. Админ-процессы | Разовые задачи — одноразовые команды в том же образе: `docker compose run --rm hub --review-login-hash …`, резервная копия `sqlite3 .backup` (выше). |

## Состав

| Файл | Что это |
|---|---|
| `Dockerfile` | Сборка образа hub: node (web, пакет агента) → rust (бинарник) → debian-slim |
| `compose.yml` | `hub` + `caddy`, том `hub-data`, жёсткие ограничения контейнеров |
| `Caddyfile` | HTTPS и проксирование (`/ui`, `/mobile/ui`, `/agent` — WebSocket) |
| `.env.example` | Все переменные с пояснениями |
| `install.sh` | Всё одной командой: `.env`, hub, подключение этого сервера, ссылка владельца |
| `init.sh` | Создаёт `.env` и генерирует секреты |
| `connect-host.sh` | Подключает этот сервер как машину владельца (от root, после `up`; `--force` — заново) |
| `llm.sh`, `compose.llm.yml`, `llm_admin.py` | Необязательный LLM-шлюз (Bifrost + CLIProxyAPI): включение, учётки подписок, провайдеры, ключи людей |
| `agent-release/` | Сюда кладётся подписанный релиз агента перед сборкой (необязательно) |
